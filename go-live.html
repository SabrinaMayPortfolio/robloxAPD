Case study 03

Waypoint: a go-live companion for implementation PMs

Waypoint is an operational companion that carries a project manager's context through a hospital software go-live, from onsite orientation to a verified correction.

  • RoleProduct designer, solo
  • TypeDesign intervention, concept
  • DomainHealthcare operations
  • ScopeWorkflow mapping, IA, interaction design, working build
  • ToolsFigJam, Figma, Claude
  • DataSynthetic

What the design delivers

  • 11 to 1places the PM had to check, carried in one companion
  • 12steps in the hero flow, proven in lo-fi before any code
  • Zeroretyping of hospital, unit, room, or device across map, issue, amendment, and chat

Concept with synthetic data. Not yet tested with project managers.

What I did

  • Mapped my own go-live pain points
  • Synthesized them into one root problem
  • Scoped and cut the feature set
  • Designed the IA, lo-fi storyboard, and hero interaction
  • Built the working prototype with Claude from my storyboard, implementing decisions I had already made

00 Problem

The context doesn't travel with the work.

The loop

  1. 01Leave the current task
  2. 02Find another system or person
  3. 03Reconstruct the missing context
  4. 04Return and resume
↻
So what

The problem isn't too many apps. The PM has become the integration layer. The fix is a companion that brings context to the moment it's needed, not a dashboard that shows everything.

01 Research

Kept raw, it read like a complaint. Grouped, it became a diagnosis.

I wrote every frustration from memory in the order it happens on a trip, before analyzing anything.

So what

Ordering by the trip, not by severity, showed where friction stacks up: arriving onsite with a clinician waiting.

02 Synthesis

Four themes. One behavior underneath them.

  • Logistics and admin

  • Orientation and wayfinding

  • People and communication

  • Operational context

These were analytical categories, not navigation. The obvious move was to ship four tabs named after them. I didn't.

So what

Every theme traced back to the same loop: leave, search, reconstruct, return.

03 Ideation

I cut real problems on purpose to design the one that mattered.

Primary user
An implementation PM onsite.
Window
Final preparation through active onsite support, where scattered information turns into immediate friction.

Golden journey

  1. 01Prepare
  2. 02Arrive
  3. 03Orient
  4. 04Support
  5. 05Encounter issue
  6. 06Investigate

Hero interaction

Kept

  • Today brief
  • Onsite floor and unit map
  • Staff and role context
  • Create an issue from location and device
  • Permitted device information
  • Similar issue retrieval
  • Routing, ownership, status
  • Amendments

Cut

  • Full reimbursement
  • Full travel management
  • Generic dashboard metrics
  • Rebuilding secure messaging
Decision
Cut reimbursement and travel, even though they were real frustrations.
Why
They're administrative problems that already have owners elsewhere.
Tradeoff
The product doesn't fix every pain I listed, so it can fix the costly one well.

Naming check

Ask a narrow question

What you're seeing
“Is LABPRNTR402 the correct printer name for ER-110?” The assistant compares the naming convention, the registered identifier, and the observed identifier, then drafts a report that opens a secure chat with Hospital IT, without exposing the full device inventory.

Decision calloutReporting

Decision
Every device on the map is a reporting surface.
Why
No sensor knows a workstation was moved; the only source of truth is a person in the room.
Tradeoff
The map is no longer read-only, so reporting must stay lightweight.

Decision calloutAI scope

Decision
AI answers narrow questions against permitted records.
Why
PMs often lack clearance to browse device data, which creates dead ends.
Tradeoff
The PM gets an answer, not the client's full inventory.

Decision calloutVerification

Decision
Corrections stay pending until Hospital IT verifies.
Why
In a hospital, the audit trail is the point.
Tradeoff
The fix is useful immediately but not authoritative until reviewed.

AI does

  • Retrieve relevant context
  • Connect permitted sources
  • Recognize similar issues
  • Prefill details
  • Suggest a likely owner

The human does

  • Observe physical reality
  • Verify context
  • Edit or reject suggestions
  • Approve the amendment
  • Resolve and close

05 Outcomes

A working build, and four questions I'd test first.

Built

Seven views (Today, Map, Issues, People, Chats, Amendments, Project), building-wide wayfinding, a unit map with clickable devices, the discrepancy-to-amendment flow, the naming check that opens a secure chat, similar-issue retrieval, and routing with a recommended owner.

Test plan

  1. 01

    Does starting from the map remove re-entry, or do PMs still reach for familiar systems?

  2. 02

    Can a PM tell an amended value from a confirmed one at a glance, mid-shift?

  3. 03

    Does a narrow AI answer about protected data feel trustworthy, or evasive?

  4. 04

    Does explicit ownership reduce messaging around to find who acts next?

Honesty note

The part I'm least sure about is the amendment. It's the right systems answer, but it asks a busy PM to accept the fix isn't finished. If that friction is unacceptable, I'd redesign the verification handoff, not let the app overwrite the record.

06 Reflection

Group the pain before you design the product.

  1. 1

    Diagnose before designing.

    The affinity map turned a list of complaints into one root cause.

  2. 2

    Cut on purpose.

    Leaving out real frustrations let the core interaction be excellent.

  3. 3

    Model uncertainty, don't hide it.

    Pending states and named owners keep people accountable for consequential changes.

Where I've applied it since

  • Lesson: diagnose before designing

    I turned my Epic experience into the brief

    The operational instincts from supporting go-lives became a structured problem, scope, and design.

  • Lesson: decide before you build

    I built with AI only after the storyboard

    Every behavior was settled in lo-fi first, so the build implemented decisions instead of improvising them.

  • Lesson: context should travel with the work

07 The long view

From one go-live to the whole implementation.

Over a few years, the same object model could extend beyond the go-live window to the full implementation lifecycle and across hospitals, with permissions, provenance, and audit history as shared building blocks rather than features bolted onto each screen.
